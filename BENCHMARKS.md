## How each number is measured

| Number | Tool | Command | Recorded in |
|---|---|---|---|
| Instructions per inference | Spike with the custom-instruction extension | `make -C firmware run` | `results.firmware` |
| Clock cycles per inference | PicoRV32 SoC compiled to C++ with Yosys CXXRTL; the firmware reads `rdcycle` | `bash hardware/scripts/soc_sim.sh mnist` | `results.soc` |
| Cycles with wait states | Same simulation; the testbench delays every memory reply | `bash hardware/scripts/soc_sweep.sh` | `results.socSweep` |
| LUTs, flip-flops, DSP blocks | `synth_ecp5` and `synth_ice40 -dsp` in Yosys | `bash hardware/scripts/soc_synth.sh` | `results.socArea` |
| Fmax | nextpnr-ecp5, LFE5U-25F CABGA256, three placement seeds | `bash hardware/scripts/soc_synth.sh` | `results.socArea` |
| Unit and wrapper correctness | RTL against 25,088 golden vectors | `bash hardware/scripts/cosim.sh` | `results.cosim` |

CI re-runs the Spike, co-simulation and SoC simulation numbers on every push and compares them with the recorded file, and also checks that Spike and the RTL agree on every instruction count. The wait-state sweep and the area and Fmax numbers depend on tool builds and take longer, so they are recorded by hand and not re-checked in CI; the 0-wait-state row of the sweep is cross-checked against the SoC run.

## Workload

One inference of the 784-128-10 INT8 MLP on one MNIST image takes 101,632 multiply-accumulates. The firmware runs ten test images (one per digit), 10 of 10 are classified correctly, and every output byte matches the C++ engine for all five code versions. Each version runs the same network; only the inner loop differs.

| Version | Inner loop |
|---|---|
| Scalar, plain | Byte loads and `mul`, one multiply-accumulate per step |
| Scalar, unrolled | The same, 16 multiply-accumulates per loop step |
| `simd_mac_clr` + `add` | One custom instruction per four multiply-accumulates, an `add` to carry the running total |
| `simd_macz` / `simd_macc` | The running total stays inside the unit |
| `simd_macz` / `simd_macc`, unrolled | The same, 8 custom instructions per loop step |

The fair comparison is the two unrolled versions, because unrolling helps both and only the hardware differs between them.

| Scalar, unrolled | 435,282 | 4.3 |

## Clock cycles per inference (PicoRV32, no wait states)

| Version | Instructions | Clock cycles | Cycles per instruction | Cycles vs plain scalar |
|---|---|---|---|---|
| Scalar, plain | 822,232 | 4,416,182 | 5.4 | 1.00x |
| Scalar, unrolled | 435,282 | 2,583,289 | 5.9 | 1.71x |
| `simd_mac_clr` + `add` | 187,598 | 1,014,656 | 5.4 | 4.35x |
| `simd_macz` / `simd_macc` | 161,500 | 908,620 | 5.6 | 4.86x |
| `simd_macz` / `simd_macc`, unrolled | 95,120 | 577,451 | 6.1 | 7.65x |

Fair speed-up in cycles: **4.47x**. Against the plain scalar loop the same hardware gives 7.65x, a figure that mixes the effect of the hardware with the effect of unrolling and is not used as the headline. The same scalar code on the core without the unit takes 4,416,182 cycles, exactly the same as with it.

| 8 | 7,561,937 | 1,766,435 | 4.28x |

PicoRV32 has no cache and fetches every instruction from memory, so memory time grows with the instruction count and the speed-up stays nearly flat. A core with caches or tightly coupled memory would behave differently, and that is not measured here.

### Wall-clock estimate

One inference with the unrolled scalar loop: 2,583,289 cycles at 84.8 MHz is **30.5 ms**. With the unit: 577,451 cycles at 72.8 MHz is **7.9 ms**. That is **3.8x** faster, less than the 4.47x in cycles, because the unit lowers the clock speed by 14%. Both clock speeds are the best of three placement seeds; the estimate takes no memory system into account.

## Correctness runs

- Unit against golden vectors: 25,088 vectors, 0 mismatches.
- Custom-0 wrapper as an instruction stream: 25,088 instructions with 3,115 idle cycles mixed in, 0 mismatches.
- Self-test of the custom instructions on the PicoRV32 SoC: 14,005 checks, all pass.
- The same self-test on a core built without the unit stops on an illegal instruction; CI requires that, so the test is known to be able to fail.

## What is not measured

- Memory is a flat array with a fixed number of wait states. No cache, no real DRAM or flash timing.
- PicoRV32 with its fast multiplier is the baseline. With the small serial multiplier the scalar code would be slower and the gain larger; that was not run.
- Xilinx 7-series timing and any ASIC flow were not run. iCE40 numbers for the full SoC are synthesis only.
- Clock speeds come from nextpnr on one device family, with three placement seeds; they are not silicon measurements.
- Both sides are compiled C at `-O2`. Hand-written assembly for either side was not tried.
- One network (784-128-10 MLP) on one dataset. Other layer shapes were not run.
- Power was not measured.

## Reproduce

```bash
bash firmware/setup_toolchain.sh && export PATH="$HOME/.riscv-edge-ai-tools/bin:$PATH"
mkdir -p build
make -C firmware run | tee build/firmware_run.txt
bash hardware/scripts/cosim.sh | tee build/cosim.txt
bash hardware/scripts/soc_sim.sh isa   | tee build/soc_isa.txt
bash hardware/scripts/soc_sim.sh mnist | tee build/soc_mnist.txt
bash hardware/scripts/soc_sweep.sh | tee build/soc_sweep.txt
bash hardware/scripts/soc_synth.sh | tee build/soc_synth.txt
python3 scripts/record_results.py       # rewrite web/js/results.js
python3 scripts/gen_benchmarks.py       # rewrite this file
```
